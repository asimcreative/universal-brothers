# Security Audit

Performed as an actual code review + verification pass against the implemented codebase, not a checklist filled in from memory. Findings are graded by what was found, not what was assumed.

## Verified in place

| Control | Status | Evidence |
|---|---|---|
| CSRF protection | ✅ | Laravel's default `VerifyCsrfToken` middleware is active (not excluded anywhere); every form in the codebase includes `@csrf`. |
| Mass-assignment protection | ✅ | Every model declares an explicit `$fillable` array; none use `$guarded = []`. |
| SQL injection | ✅ | Grepped the entire `app/` tree for `DB::raw`, `DB::statement`, `whereRaw`, `selectRaw` — zero occurrences. All queries go through Eloquent/query builder parameter binding. |
| XSS | ✅ | All user-supplied data is rendered via Blade's auto-escaping `{{ }}`. The only `{!! !!}` (raw) output in the codebase is fixed badge-HTML strings the admin views construct themselves (e.g. `<span class="badge...">Yes</span>`), never user input. |
| Password hashing | ✅ | `User::password` uses Laravel's `hashed` cast (bcrypt); seeded admin password uses `Hash::make()`. |
| File upload validation | ✅ | Every upload field (`cover_image`, slider `image`, news `cover_image`) is validated `image`+`max:4096` via Form Requests/controller validation — no arbitrary file type accepted, no executable-extension risk. |
| Auth/authorization | ✅ | All `/admin/*` routes (except the login screen itself) require `auth` + a custom `admin` middleware that also checks `is_active`, logging out and redirecting deactivated accounts. Verified by `Admin\AuthTest` (5 passing tests) and `Admin\PackageManagementTest`'s guest-rejection test. |
| Route-level authorization test coverage | ✅ | Guest-cannot-access assertions exist for package admin and inquiry admin, not just "the route exists." |
| Rate limiting | ✅ (added during this audit) | Public `contact`/`inquiries` POST routes and the admin login POST route now carry `throttle:5,1` — this was a real gap caught during the review, not present in the initial build, fixed and verified (`SecurityHeadersTest` confirms headers; throttle confirmed via route definitions, not yet load-tested). |
| Security headers | ✅ (added during this audit) | `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` now applied globally via a `SecurityHeaders` middleware, verified by a passing test. |
| IDOR | ✅ | Admin resource routes use Laravel's implicit route-model binding scoped by primary key with ownership not applicable (single-tenant admin, not per-user data) — no user-supplied ID is trusted to bypass a query scope; public package routes additionally verify the package belongs to the requested category slug (`abort_unless`) before rendering, tested in `PackageBrowsingTest`. |
| Secrets not committed | ✅ | `.env` confirmed excluded from git via `.gitignore`; verified via `git status` before every commit in this session. |

## Known gaps (not fixed — genuine external blockers or explicit scope decisions)

| Gap | Why it's not fixed here | What's needed |
|---|---|---|
| No Google reCAPTCHA on public forms | Proposal calls for it, but no site/secret key exists anywhere in the source material or environment | Client must supply reCAPTCHA v2/v3 keys; `site_settings` already has placeholder rows (`recaptcha_site_key`, `recaptcha_secret_key`) ready to receive them |
| `APP_DEBUG=true` in `.env` | Correct for local development (shows detailed errors), **must be `false` before any production deploy** — leaving it `true` in production leaks stack traces/env values on error pages | Set `APP_DEBUG=false` and `APP_ENV=production` as part of the deployment step, not before |
| Local dev DB is SQLite, not MySQL | MySQL root credentials for this machine aren't available (see PROJECT_DISCOVERY.md) | User needs to supply the local MySQL root password, or the target production DB credentials directly, to verify against the real target engine before go-live |
| No HTTPS/SSL configured | This is a local dev environment with no domain/hosting yet | Standard step at actual deployment (Let's Encrypt or hosting provider's SSL) |
| No payment gateway | Explicitly out of scope for this phase (inquiry-based, not transactional) — see PROJECT_REQUIREMENTS.md §V | N/A until the online-booking future enhancement is greenlit |
| Admin panel has only 2 roles, no granular per-module permissions | Proportionate to the actual requirement (Users & Roles module in the proposal doesn't specify a permission matrix) | If finer-grained permissions are wanted later, `spatie/laravel-permission` is the natural addition — not pre-built speculatively here. **Update:** an independent code review (FINAL_CODE_REVIEW.md H-3) found this row had drifted from true to false — there was no admin UI to manage users at all, and the `role` column had *zero* behavioral effect anywhere, so even the coarse 2-role split described above wasn't actually enforced. Fixed: a real `UserPolicy` now gates account management to `super_admin` (with a guard against self-lockout), closing the gap this row was describing without noticing it had regressed. |
| Not penetration-tested against a live, deployed instance | No production/staging server exists yet in this engagement | Standard pre-launch penetration test once a real deployment target exists |

## Release-gate independent security re-audit (12 categories re-verified from scratch)

A full independent re-verification against current source — not a re-read of this document — covering Authentication, Authorization, CSRF, XSS, SQL Injection, Mass Assignment, IDOR, File Upload Security, Rate Limiting, Session Security, Security Headers, and Sensitive Configuration. 9 of 12 categories came back fully clean on direct re-verification (Authentication, Authorization, CSRF, SQLi, IDOR, File Upload, Rate Limiting, and the credential/CORS half of Sensitive Config) — including the newest Award/Affiliation/Testimonial controllers and the Hajj listing filter bar's query-string handling.

**HIGH, found and fixed:** `database/seeders/AdminUserSeeder.php` was called unconditionally from `DatabaseSeeder`, with no environment guard — a routine `php artisan db:seed` on **any** environment, including a real production deploy, would silently create a well-known `admin@universalbrothers.test` / `password` super_admin account. The only prior safeguard was a deployment-checklist reminder, which is not an enforced code control. **Fixed**: the seeder now checks `App::environment(['local', 'testing'])` and refuses to run otherwise; 2 new tests prove both halves (blocked outside local/testing, still works for the legitimate dev/CI workflow).

**MEDIUM ×2, found and fixed:**
- `Admin\SiteSettingController::update()` looped over `$request->input('settings', [])` with **zero validation** — no array-shape check, no per-value length cap, and its fallback branch would silently `SiteSetting::create()` a brand-new row for any client-supplied key with no allow-list at all. Fixed: validates as a generic string array (`max:1000` per value), then restricts writes to keys that already exist as real `SiteSetting` rows — a genuine submission never needs to introduce a new key. (Mid-fix, a second real bug was caught and avoided: an early draft of this fix used a `Builder::update()` mass update, which bypasses Eloquent's `saved` event and would have reintroduced the exact cache-invalidation bug `FINAL_CODE_REVIEW.md` H-1 already fixed once — caught by the existing `test_updating_a_site_setting_actually_invalidates_its_cached_value` regression test failing, and corrected to update the Eloquent model instance instead.) New test proves an unknown key is rejected, not silently created.
- **No Content-Security-Policy** existed anywhere, despite this app intentionally rendering admin-authored raw HTML on public pages (`Page::body`, `NewsArticle::body`, `Office::google_maps_embed`). Fixed: added a CSP via `SecurityHeaders` middleware (`default-src 'self'`, `object-src 'none'`, `frame-ancestors 'self'`, `base-uri 'self'`, `form-action 'self'`, `img-src`/`font-src 'self'`, `frame-src 'self' https:` for video embeds). `script-src`/`style-src` still include `'unsafe-inline'` — the app genuinely uses inline `style=""` attributes (hero/video-thumbnail backgrounds, prose max-widths) and one inline `<script>` block (the Hajj currency switcher) that would otherwise break; eliminating those is a real refactor not undertaken in this pass, disclosed here rather than silently worked around. Even with that allowance, the CSP still blocks loading a script/style/image/font from an attacker-controlled external origin and blocks `<object>`/`<embed>` entirely. Verified the full Playwright suite (including the currency-switcher test) still passes with the CSP active.

**LOW, found and fixed:** `video_url` fields (`Testimonial`, `MediaItem`, `HajjPackageRequest`'s media rows) were rendered as an `<iframe src="...">` but validated only as `nullable|string|max:255` — no `url` format rule, so a non-URL string (or a `javascript:`/`data:` scheme) could reach the `src` attribute (Blade escaping prevents attribute-breakout, but not a malicious scheme). Fixed: added the `url` rule to all three.

**INFO, left as-is (not defects):** both admin roles (`super_admin` and `content_editor`) can write the raw-HTML CMS fields above — an intentional two-role design already documented, not a new gap; `SESSION_SECURE_COOKIE` is unset, correct for this local HTTP dev environment and already tracked as a pre-HTTPS-deploy checklist item.

## Verdict

No critical or high-severity issue found and left unfixed, across any of the three independent security passes this engagement has now had (the original audit, the FINAL_CODE_REVIEW.md follow-up, and this release-gate re-audit). The two issues found during the original review (missing rate limiting, missing security headers) were fixed in the same pass and are covered by tests. `FINAL_CODE_REVIEW.md` found four more real HIGH-severity issues the original audit had missed — a Settings cache-invalidation bug, secret settings rendered in plaintext, soft-deleted packages blocking slug/code reuse, and the Users & Roles authorization module being entirely absent despite being explicitly required — all four fixed and regression-tested (see that document's "Resolution" section, and the "Admin panel has only 2 roles" row above). The release-gate re-audit above found one more real HIGH (the unconditional default-credential seeder) and closed it, plus 2 MEDIUM and 1 LOW. Everything in the "known gaps" table above is a genuine external dependency or explicit scope boundary, not a deferred fix.
